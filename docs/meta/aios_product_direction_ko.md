## 1. 제품 목적

AIOS는 **AI가 자신의 작업 공간과 현재 상태를 이해하고, 로컬 자원을 효율적으로
사용하며 안정적으로 활동하고, 사용자와 지속적으로 상호작용하는 운영 환경**을 만든다.
이 목적은 2026-09-09 사용자가 명확히 한 제품 방향이다.

세 가지 제품 가치를 함께 평가한다.

1. **공간과 상태의 인지:** 자신이 연결된 실행 환경, 작업 대상, 사용 가능한 도구,
   현재 작업과 결과, 관측되지 않은 부분을 구분할 수 있다.
2. **편안하고 효율적인 활동:** 필요한 상태를 적은 추측과 반복 조회로 얻고,
   작업을 시작·관찰·중단·복구할 수 있다. 모델과 하드웨어 자원의 로컬 효율도 여기에 포함한다.
3. **사용자와의 상호작용:** 사용자가 작업 중에도 질문·수정·취소·개입할 수 있고,
   AI는 현재 행동과 결과를 이해하기 쉬운 방식으로 보여 준다. 대화와 작업 대상이 연결된다.

Kernel Room은 이 경험을 뒷받침하는 관리 핵심이다. 계층·드라이버·검증 항목의 수만으로
제품 목적의 달성을 판정하지 않는다. 각 작업은 개선되는 사용자/에이전트 경험과 이를
증명할 관찰 가능한 결과를 함께 적는다.

## 3. AI가 인지하는 공간

여기서 공간은 **AI가 작업하며 확인할 수 있는 대상·관계·상태·행동 범위**다.
화면상의 방, 창, 지도는 이를 표현할 수 있는 선택지다. 공간 인지의 검증 대상은
외부에서 확인 가능한 정보 사용과 행동이며, 모델의 주관적 의식 여부가 아니다.

에이전트가 다음 질문에 근거와 함께 답할 수 있도록 한다.

| 질문 | 필요한 정보 | 혼동을 막는 경계 |
|---|---|---|
| 나는 지금 어디에서 실행되는가? | host와 서비스 실행 인스턴스, 연결된 관리 대상 | Linux PID와 AIOS Node ID를 동일시하지 않음 |
| 지금 무엇을 보고 있는가? | 파일·서비스·사용자 선택·작업 결과와 관측 시점 | 오래된 기록과 현재 관측, 미관측과 값 0을 구분 |
| 무엇을 할 수 있는가? | 사용 가능한 작업, 입력 조건, 실제 허용 범위 | 기능 존재·실행 준비·사용 권한을 구분 |
| 무엇을 하고 있었는가? | 요청, 진행 상태, 완료된 단계, 결과의 위치 | 대화 요약과 실제 실행 기록을 구분 |
| 누가 무엇을 바꿨는가? | 사용자 개입, 모델/서비스 교체, 대상 변경 | 이전 세대의 관계를 새 실행에 암묵적으로 재사용하지 않음 |
| 다음에 무엇을 확인해야 하는가? | 실패 이유, 불확실한 결과, 가능한 복구 | 결과를 모르는 작업을 성공이나 미실행으로 단정하지 않음 |

현재의 하드웨어 inventory와 resource snapshot은 이 공간에 들어올 **관측 원본**이다.
그 자체가 통합된 공간 인지 인터페이스는 아니다. 향후 파일·도구·작업·사용자 선택을
표현할 때도 실제 source와 유효성을 연결한다.

작업, 세션, 결과물은 제품 상호작용에 필요한 기록이다. 이들을 Room 아래의 새 관리
계층으로 자동 추가하거나 Cell/Node/NodeBit와 같은 ID로 취급하지 않는다. 연결이 필요한
경우 관리 모델의 명시적 adapter와 binding 계약을 따른다. UI의 방이나 거리도 Cell·Orbit의
구현 증거가 아니다.

## 4. 사용자와 함께 활동하는 방식

아래는 후속 구현을 평가할 **제품 요구사항**이다. 현재 CLI가 모두 제공한다는 뜻이 아니다.

- 사용자는 현재 연결 상태, AI의 작업 대상, 진행 중인 일과 결과를 볼 수 있다.
- 작업 도중 질문하거나 대상을 바꾸면 기존 작업과 새 요청의 관계를 명확하게 처리한다.
- 취소 요청을 받았다는 표시와 실제 실행이 멈췄다는 결과를 구분한다.
- 이미 허용된 작업은 정해진 범위에서 진행한다. 추가 권한이나 의미 있는 선택이
  필요한 지점에서는 구체적인 대상·예상 효과·현재 상태를 보여 준다.
- 진행 알림은 시작, 의미 있는 변화, 사용자 판단 필요, 실패, 완료에 맞춘다.
  같은 상태를 반복 통보하는 빈도를 제품 성과로 계산하지 않는다.
- 모델 응답, 도구의 실행 결과, 외부에서 확인한 증거를 구별해서 보여 준다.
- 모델이나 세션이 바뀌면 보존된 작업 기록을 다시 확인한다. 대화가 이어졌다는 이유로
  이전 실행 대상·권한·완료 상태까지 유효하다고 추론하지 않는다.

사람이 읽는 CLI/화면과 에이전트가 읽는 구조화된 인터페이스는 같은 상태와 결과를
설명해야 한다. 구현용 schema 번호나 원시 PID를 일반 사용자 흐름의 필수 지식으로 만들지
않고, 진단할 때 원본 증거를 열 수 있게 한다.

## 5. 유지할 구조와 실행 책임

- **관리 핵심:** Room → Cell → Node → NodeBit의 의미, 세대, 유효성, source 결속은
  AIOS의 관리 모델이 소유한다. 모델이 출력한 자기 설명만으로 관리 상태를 확정하지 않는다.
- **에이전트 활동:** 자유 형식 추론, 대화, 문맥 구성과 도구 조합은 userspace/runtime에서
  다룬다. 현재 검증된 좁은 실행 경로를 바탕으로 확장한다.
- **Linux 실행 기반:** 현재 운영 이미지의 특권 커널·드라이버·프로세스·네트워크를 제공한다.
  이는 현재 실용적인 delivery 경로이며 자체 native 커널의 Linux 드라이버 직접 호환 증거가 아니다.
- **자체 native 커널:** 독자적인 x86_64 구현과 관리 불변식의 기준·증명 경로를 유지한다.
  자체 커널이 실제 운영을 맡는 범위는 별도 native 실행 증거로 평가한다.

에이전트 사용성이 높아지는 것과 native 커널의 실행 책임이 넓어지는 것은 별도 성과다.
어느 한쪽을 다른 쪽의 완료로 표시하지 않는다. 독자 커널 목표와 Linux-hosted 제품 개발의
접점은 공통 관리 의미를 실제로 검증하는 데 있으며, 전체 cross-backend conformance는 후속이다.

보존된 v0.7의 `request_body()`는 고정 system 문장과 이번 사용자 prompt만 전달했다.
v0.8 개발 경로는 MAIN 자신의 제한된 환경 관측과 질문을 명시적으로 묶고, 오래된 값과
미관측 항목을 구분한다. 이전 대화와 사용자 선택 작업공간의 자동 문맥은 아직 없다.
환경 표시, 실제 입력 bytes, 모델이 그 문맥을 사용한 결과의 검증은 각각 구분한다.
CPU/RSS 관측도 효율 개선의 측정 재료이며 개선 자체를 증명하지 않는다.

`SUPPORTING`은 관리 모델에 대한 기여 분류이고 `PARTIAL`은 구현 성숙도다.
제품 목적에는 상호작용 자체도 직접 기여한다. 관리 계층을 수정하지 않았다는 이유로
사용자 개입·관측 가독성·작업 복구의 제품 가치를 제외하지 않는다.

## 7. 제품 성공을 입증하는 장면

다음 장면은 acceptance 요구사항이며, 실행 순서·선행조건은 전역 작업흐름이 정한다.

1. **첫 접속:** 에이전트에게 실제 전달한 환경·작업공간 문맥의 출처·시점·범위를 남기고,
   에이전트가 확인된 상태와 모르는 부분을 구분하며,
   사용자가 같은 상태를 이해할 수 있다.
2. **한 작업:** 유효한 실행 대상을 확인해 요청을 처리하고, 사용자에게 결과와
   확인 가능한 산출물을 돌려준다.
3. **작업 중 대화:** 사용자 질문·수정·취소가 실행 상태와 연결되며, 작업 완료/중단 여부가
   실제 실행 증거와 일치한다.
4. **실행기 교체:** 오래된 관계를 거부하고, 필요한 복구를 설명한 뒤 허용된 절차로 다시 연결한다.
5. **재접속:** 완료·미완료·결과 불명 상태를 보존된 기록과 실제 실행에서 확인한다.
   결과가 불명인 변경 작업을 무조건 재실행하지 않는다.

측정은 같은 작업·모델·하드웨어 조건에서 한다. 완료율, 사용자의 추가 개입 횟수,
상태 오해·중복 실행 여부, 중단 확인 시간, 복구 성공률, 응답 지연, CPU·메모리를
함께 기록한다. 현재 이 지표들의 제품 baseline이나 타 프로젝트 대비 우위는 확정하지 않는다.

## 8. 문서와 정보의 신선도

작업자는 [통합 진입 가이드](integrated_work_guide_ko.md)에서 현재 질문의 사실 소유자를
고르고, [신선도 원장](document_freshness_registry_ko.md)에서 최근 검토 범위와 재검토
조건을 확인한다. 제품 목적, 전역 우선순위, 관리 계약, 실제 실행 증거를 한 파일에
중복해서 유지하지 않는다.

같은 원칙을 향후 에이전트의 공간 정보에도 적용한다. 관측 시점, 출처, 유효성,
실행 인스턴스를 확인할 수 있어야 한다. 문서의 검토일 갱신은 실행 증거의 갱신이 아니고,
제품 화면의 최근 갱신 표시도 연결된 모든 원본이 최신이라는 뜻이 아니다.

## 9. 이번 개정의 범위

2026-09-09의 문서 정비 단계는 제품 목적과 작업 판단 기준을 정리했다. 이 단계에서는
기존 K/H/M/C/W 등의 기술축·ABI·runtime·검증 판정과 과거 실행 증거를 변경하지 않았다.

위 표와 환경 문맥 가이드에서 별도 평가한다. native ABI와 보존된 과거 실행 증거는 그대로다.
